ZASADY ARCHITEKTONICZNE I INWARIANTY WYKONAWCZE SYSTEMU ADK:

1. Grupowanie domenowe (Domain-Grouped Layout):
   Zamiast nazw warstw w ścieżkach, katalogi `adk/agents/` oraz `adk/tools/` są
   zorganizowane według czterech domen funkcjonalnych: `planning` (W1), `building` (W2),
   `verification` (W3) oraz `evolution` (W4). Wewnątrz `adk/tools/` obowiązuje
   twardy zakaz używania redundantnego słowa `tool`/`tools` w nazwach plików
   i podkatalogów (weryfikowany przez test `tests/test_repository_hygiene.py`).

2. Deklaratywność agentów (.md):
   Wszyscy agenci są zdefiniowani jako ustrukturyzowane pliki Markdown w
   `adk/agents/<domena>/`. Kod Pythona (`adk/core/llm.py`) wczytuje prompt
   systemowy z pliku `.md`, dokleja ładunek wejściowy w sekcji
   `=== INPUT JSON PAYLOAD ===` i wymusza odpowiedź w formacie ścisłego JSON-a.

3. Nienaruszalność strażników (GUARD Immunity):
   Agenci pełniący rolę sztywnych bramek jakościowych (`task_critic_guard.md` w W1
   oraz `redteam_critic_guard.md` w W3) są całkowicie odporni na mutację promptów
   (`agent_mutator.py`) oraz podział (`agent_splitter.py`). Żadna pętla ewolucyjna
   nie może osłabić kryteriów akceptacji.

4. Jawny stan w JSON (`adk/state/`):
   Komunikacja między warstwami, orkiestratorem i narzędziami odbywa się wyłącznie
   poprzez serializację do 7 jawnych plików JSON obsługiwanych przez modele
   danych z `adk/core/models.py`. Stan jest w 100% audytowalny i odtwarzalny.

5. Uziemienie symboliczne (Zero Memory Numbers & Zero Hallucination):
   Tekst pracy dyplomowej (`.md`/`.tex`) nie może zawierać wpisanych z pamięci
   modelu hiperparametrów ani wyników liczbowych. Każda stała kodu wymaga wskaźnika
   `\ref_ast{plik:symbol}`, każda metryka eksperymentalna wskaźnika
   `\ref_csv{plik:wiersz:kolumna}` lub `\ref_csv{plik:kolumna}`, a każde odwołanie
   do wykresu/ryciny wskaźnika `\ref_fig{plik_lub_id}`, kompilowanych
   deterministycznie przez `ref_compiler.py`.

6. Świeżość artefaktów (`mtime` Invariant) i Edge-Scoped Verification:
   Plik wynikowy `results.csv` musi zawsze posiadać znacznik czasu modyfikacji
   (`mtime`) nowszy niż wszystkie pliki źródłowe `.py` w `adk/workspace/`.
   Weryfikacja Warstwy 3 jest selektywnie dobierana do zakresu hiperkrawędzi
   (`Edge-Scoped Verification`) — węzły czysto kodowe (`v1`, `v2`, `v5`) nie
   uruchamiają fałszywych alarmów przestarzałości tabeli CSV.

7. Trzy interaktywne bramki promotorskie HITL (`state/hitl_flag.json`):
   Proces powstawania pracy i oprogramowania przechodzi przez 3 punkty kontrolne:
   - `GATE_1_OUTLINE_APPROVAL` (zatwierdzenie tezy, zakresu i planu zadań),
   - `GATE_2_METHODOLOGY_APPROVAL` (zatwierdzenie architektury po bramce Guard W1),
   - `GATE_3_DEFENSE_APPROVAL` (końcowe dopuszczenie do obrony po audycie Red-Team W3).
   Bramki mogą być zatwierdzane automatycznie, przez callback API lub interaktywnie
   w konsoli dzięki fladze `--interactive-gates`.

8. Pełna Obserwowalność Decyzji i Promptów LLM (Nowość ADK 2.0):
   Wszystkie wywołania LLM (Google Gemini, Ollama, Mock) są natychmiast logowane
   na żywo do konsoli w ujednoliconym formacie:
   `[LLM DECISION: <agent>] (<provider>:<model>, <tier>, <ms>) -> <decyzja>`.
   Każde zadanie benchmarkowe generuje w swoim dedykowanym katalogu:
   - `llm_interactions.md` (czytelny dokument z tabelą decyzji i rozwijanymi
     blokami pełnego promptu oraz surowej odpowiedzi),
   - `llm_interactions.jsonl` (pełny zrzut maszynowy).
   Dostępny jest także tryb pełnego podglądu w terminalu: `--verbose-llm` / `-v`.

9. Wielofalowa Realizacja Wielocyklowa (Multi-Cycle Architectural Waves):
   Obsługa flagi `multi_cycle_waves=True` w orkiestratorze, która przeprowadza
   kolejno pełne pętle naprawczo-ewolucyjne:
   `W2 -> W3(FAIL) -> W4(MUTATE/CREATE/SPLIT) -> W1(FIX) -> W2 -> W3(PASS)`
   dla każdego z kluczowych węzłów: kodu (`v1`), eksperymentu (`v3`) i pracy (`v4`).

10. Kompletność Wydawnicza i Autonomia (Thesis Bundle Publishing):
    System nie generuje wyłącznie fragmentów kodu, lecz kompletny, autonomiczny
    pakiet inżynierski: pełną 6-rozdziałową pracę dyplomową (PDF + LaTeX + HTML),
    skrypt uruchomieniowy eksperymentu `run_experiment.py`, wektorowe wykresy
    porównawcze oraz bibliografię BibTeX.

MODUŁ 0.2: Konektor Wielodostawcowy LLM (`adk/core/connection.py`)
--------------------------------------------------------------------------------
[x] Ładowanie zmiennych środowiskowych (`load_dotenv_file`):
    - Bez zewnętrznych zależności parsuje pliki `.env` z katalogu głównego projektu
      oraz z `adk/.env`, ustawiając klucze w `os.environ`.
[x] Klasa `LLMConnectionManager`:
    - `resolve_provider()`: wybiera dostawcę według priorytetu:
      1. Jawnie przekazany argument `provider` (`"google"`, `"ollama"`, `"mock"`),
      2. W trybie `"auto"`: jeśli w środowisku istnieje `GEMINI_API_KEY` lub
         `GOOGLE_API_KEY` -> `"google"`; jeśli `HARNESS_USE_OLLAMA == "1"` -> `"ollama"`;
         w przeciwnym razie -> `"mock"` (deterministyczny tryb offline).
    - `resolve_model_name(provider, model_tier)`: mapuje klasę `SML` / `LRM` na model:
      * Dla `"google"`:
        - `LRM` -> `HARNESS_GOOGLE_LRM_MODEL` (domyślnie `"gemini-2.5-pro"`)
        - `SML` -> `HARNESS_GOOGLE_SML_MODEL` (domyślnie `"gemini-2.5-flash"`)
      * Dla `"ollama"` / `"mock"`:
        - `LRM` -> `HARNESS_OLLAMA_LRM_MODEL` / `HARNESS_LRM_MODEL` (domyślnie `"qwen3-coder:latest"`)
        - `SML` -> `HARNESS_OLLAMA_SML_MODEL` / `HARNESS_SML_MODEL` (domyślnie `"gemma4:e2b"`)
    - `call_google_gemini(...)`: wywołuje endpoint REST `v1beta/models/{model}:generateContent`
      z `temperature: 0.1`, `responseMimeType: "application/json"` i osobnym polem `systemInstruction`.
    - `call_ollama(...)`: wywołuje lokalny endpoint `http://localhost:11434/api/generate`
      z `stream: False`, `format: "json"` i polem `system`.
    - `check_llm_access()`: diagnostyka dostępności API i modeli w lokalnej Ollamie.

MODUŁ 0.3: Wykonywanie Agentów Deklaratywnych i Obserwowalność (`adk/core/llm.py`)
--------------------------------------------------------------------------------
[x] Funkcja `call_agent(md_path, user_payload, model_tier="SML", provider=None)`:
    1. Wczytuje treść pliku `.md` agenta jako prompt systemowy.
    2. Serializuje `user_payload` do JSON-a i buduje blok `=== INPUT JSON PAYLOAD ===`.
    3. Obsługuje trzy ścieżki wykonania:
       - Zarejestrowany callback testowy (`set_llm_handler(handler)`),
       - Wywołanie zdalnego/lokalnego API (`google` lub `ollama`) z odpornym
         parserem `_extract_json_from_text(text)` (usuwa bloki `<think>...</think>`,
         wyciąga kod z bloków ```` ```json ```` lub skanuje pierwszy poprawny obiekt
         `{...}` przez `json.JSONDecoder().raw_decode`),
       - Automatyczny fallback do `_default_simulated_response(...)` w przypadku
         trybu `"mock"`, błędu sieciowego lub niepoprawnego JSON-a z modelu.
    4. Analizuje podjętą decyzję przez `summarize_agent_decision(agent_name, payload, output)`.
    5. Real-time CLI Stream: wypisuje natychmiast zwięzłą decyzję w konsoli:
       `[LLM DECISION: <agent>] (<provider>:<model>, <tier>, <ms>) -> <decyzja>`.
       Gdy `HARNESS_VERBOSE_PROMPTS=1` lub flaga `-v`: wypisuje pełne ramki promptu i odpowiedzi.
    6. Zapisuje interakcję do telemetrii `_LLM_TELEMETRY["interactions"]`.
    7. Rejestruje pełną wymianę poprzez `HarnessProcessLogger`.

[x] Funkcja `summarize_agent_decision(...)`:
    Semantyczny ekstraktor intencji i werdyktów dla wszystkich ról: planistów, strażników,
    architekta ewolucji, konsolidatora promptów, koderów, testerów i pisarzy.

1. `state/hypergraph_matrix.json`:
   Przechowuje topologię hipergrafu projektu:
   - `nodes`: słownik wierzchołków `v1`..`v6` z polami `path`, `degree` d(v) oraz
     dynamicznie ewoluującą wagą trudności `weight` w(v) (mechanizm `EvoRoute`):

     * `v2`: `core.py` (d=3, w=1.2)
     * `v3`: `results.csv` (d=2, w=1.0)
     * `v4`: `thesis.md` (d=1, w=1.6)
     * `v5`: `test_core.py` (d=1, w=1.0)
     * `v6`: `thesis.compiled.md` (d=0, w=1.0 — artefakt wyjściowy tylko do odczytu)
   - `edges`: słownik hiperkrawędzi grupujących powiązane wierzchołki:
     * `E1`: `["v1", "v2"]` (sprzężenie konfiguracji z logiką główną)
     * `E2`: `["v2", "v3"]` (sprzężenie kodu ewaluacji z tabelą CSV)
     * `E3`: `["v1", "v3", "v4"]` (sprzężenie parametrów, tabeli CSV i tekstu pracy)
     * `E4`: `["v2", "v5"]` (sprzężenie logiki głównej z testami jednostkowymi)
   - `matrix`: binarna macierz incydencji H[v_i][E_k] in {0, 1}.

2. `state/task_queue.json`:
   Lista zadań atomowych:
   `[{"task_id": "T1", "description": "...", "target_node": "v1", "assigned_agent": "seed_coder", "status": "DONE"}, ...]`

3. `state/agent_registry.json`:
   Słownik zarejestrowanych agentów z podziałem na domeny i flagą aktywności:
   - Startowi agenci aktywni (`"active": true`, `"domain": "building"`):
     * `seed_coder` (`agents/building/seed_coder.md`, specjalizacja: `python_coding`)
     * `seed_tester` (`agents/building/seed_tester.md`, specjalizacja: `unit_testing`)
     * `seed_writer` (`agents/building/seed_writer.md`, specjalizacja: `academic_writing`)
     * `sota_researcher` (`agents/building/sota_researcher.md`, specjalizacja: `literature_review`)
   - Przy kreacji w W4 dopisywani są agenci `dyn_<slug>`, a przy podziale rodzic
     otrzymuje `"active": false` oraz `"archived_reason"`, natomiast dzieci
     `"<parent>_<sub_spec>"` otrzymują `"active": true` i przejmują zadania rodzica
     w `state/task_queue.json`.

4. `state/validation_report.json`:
   Strukturalny werdykt z Warstwy 3:
   `{"status": "PASS|FAIL", "failed_task_id": ..., "failed_node": ..., "failed_file": ..., "failed_agent": ..., "supervisors": {"code_auditor": {...}, "symbolic_auditor": {...}, "redteam_critic_guard": {...}}, "summary": "..."}`
   (nadzorcy spoza zakresu hiperkrawędzi bieżącego zadania otrzymują status
   `"SKIPPED_OUT_OF_EDGE_SCOPE"`).

5. `state/failure_ledger.json`:
   Pamięć długotrwała błędów i kompaktowań promptów:
   - `failures`: lista wpisów `{"agent": ..., "context": ..., "injected_rule": ...}`
   - `compactions`: lista wpisów z konsolidacji co 4 reguły
     `{"agent": ..., "cycle": N, "rules_consolidated_count": 4, "consolidated_rules": [...], "synthesized_invariant": "..."}`

6. `state/evolution_history.json`:
   Chronologiczny rejestr akcji Warstwy 4 i routera EvoRoute (`events`):
   typy zdarzeń: `WEIGHT_ESCALATED`, `AGENT_MUTATED`, `PROMPT_CONSOLIDATED`,
   `AGENT_CREATED`, `AGENT_SPLIT`, `VALIDATOR_PROMOTED`, `HITL_TRIGGERED`.

7. `state/hitl_flag.json`:
   Stan bramek promotorskich Human-in-the-Loop:
   `{"active": false, "current_gate": "GATE_3_DEFENSE_APPROVAL", "approved_gates": ["GATE_1_OUTLINE_APPROVAL", "GATE_2_METHODOLOGY_APPROVAL", "GATE_3_DEFENSE_APPROVAL"], "question": null, "context": {...}}`
